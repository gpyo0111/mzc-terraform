## 카드 1. S3 퍼블릭 액세스 전면 차단

**흐름:** 누가 버킷을 "전체 공개"로 만들려 함(퍼블릭 ACL/정책 `Principal:*`) → **퍼블릭 차단 4종이 무효화/거부** → 외부에서 못 봄.

**무엇 (4종 전부 ON):**
- `block_public_acls` — 새 퍼블릭 ACL 차단
- `ignore_public_acls` — 기존 퍼블릭 ACL 무시
- `block_public_policy` — 새 퍼블릭 버킷 정책 차단
- `restrict_public_buckets` — 퍼블릭 정책 가진 버킷 접근 제한
- → ACL 2개 + 버킷정책 2개 = 모든 퍼블릭 경로 봉쇄

**왜:** 음성(생체정보) 버킷 실수 노출 = 최악 → 사람이 잘못 써도 계정/버킷 레벨에서 강제 차단(안전망).

**어디:** audio/model/web-static/tf-state + cloudtrail-logs/flow-logs/athena-results.

**❓ 드릴 (보지 말고 말로):**
- Q1. 퍼블릭 차단 4종을 ACL용·정책용으로 나누면? 왜 둘 다 필요?
- Q2. 버킷정책으로 CloudFront는 허용했는데, 퍼블릭 차단이랑 안 부딪히나?
- Q3. 이게 막는 "최악의 사고"는 구체적으로 뭔가?

**💡 모범답안:**
- A1. ACL용 2개(새 퍼블릭 ACL 차단 + 기존 무시), 정책용 2개(새 퍼블릭 정책 차단 + 퍼블릭 버킷 접근 제한). 퍼블릭으로 여는 경로가 ACL·정책 두 가지라 둘 다 막아야 완전.
- A2. 안 부딪힘. 퍼블릭 차단은 `Principal:*`(누구나)인 것만 막음. CloudFront는 특정 서비스 + SourceArn 조건이라 '퍼블릭'이 아님 → 통과. (문지기 정책 + 퍼블릭 차단 안전망 = 이중 방어)
- A3. 사용자 음성 원본(생체정보) S3 버킷이 인터넷에 통째로 노출되는 사고. 개인정보 유출 + 컴플라이언스 위반.

## 카드 2. S3 등급별 수명주기 정책

**흐름:** 음성 업로드 → 등급별 폴더(`uploads/guest|free|tenants/`) 저장 → S3가 매일 객체 나이 체크 →
- guest: 7일 → 삭제
- free: 30일 → Glacier → 90일 삭제
- paid(tenants): 30일 → Glacier → 365일 삭제
- (uploads/ · results/ 각각)

**왜:** ① 비용(오래된 음성 싸게/삭제) ② 생체정보 최소보관(유출면 축소·컴플라이언스).

**용어:** Glacier = 콜드 스토리지(아주 싸게 장기보관, 꺼낼 때 시간·비용).

**❓ 드릴 (보지 말고 말로):**
- Q1. guest 음성은 며칠 뒤 어떻게? 왜 유료보다 짧게?
- Q2. "수명주기가 보안이랑 무슨 상관? 비용절감 아닌가?" 반박에 답?
- Q3. Glacier로 "이동"하는 이유? 그냥 삭제하면 안 되나?

**💡 모범답안:**
- A1. 7일 뒤 즉시 영구 삭제. guest는 체험/임시라 보관 가치 낮고 빨리 파기, 유료는 서비스 가치상 오래 보관.
- A2. 보안과 직결됨. **생체정보는 보관 자체가 위험**(들고 있는 동안 유출·오남용 가능). 최소 기간만 보관 = 유출면(공격 표면) 축소 + 개인정보보호 컴플라이언스. 비용은 부수효과.
- A3. 삭제 의무 기간 전(유료 365일 등)엔 보관해야 하므로, 그 기간 동안은 **자주 안 쓰는 데이터를 싼 Glacier로 옮겨 비용 절감**. 보관 의무가 끝나면 삭제.

## 카드 3. KMS CMK + 가드레일 (자동회전 / 삭제 타임록 / 키정책 옵션A)

**흐름:** 음성·모델을 암호화할 **전용 자물쇠(CMK)** 를 우리가 직접 만들어 둠 → 키는 **연 1회 자동 교체** + **삭제 명령 떨어져도 30일 유예** + **키 쓸 수 있는 자(ECS 역할)만 명시** → 키를 가진 자만 음성을 풀 수 있음.

**무엇 (3개 가드레일):**
- **CMK(고객관리형 키) 직접 생성** — AWS가 주는 기본키(aws/s3) 말고 우리 전용 마스터 키. 권한·정책·회전을 우리가 통제.
- `enable_key_rotation = true` — **연 1회 키 자동 교체**. 옛 키가 새도 미래 데이터는 새 키로 보호.
- `deletion_window_in_days = 30` — 삭제 눌러도 **30일 대기(타임록)**. 실수·랜섬웨어로부터 복구 여지.
- **키 정책 옵션A (2개 statement):**
  - ① `EnableIAMUserPermissions` — 계정 루트에 `kms:*`. **잠금사고(lockout) 방지** + 기존 IAM 기반 접근 유지.
  - ② `AllowECSTaskRolesUseOfKey` — **api/worker ECS 역할만** `Decrypt`/`GenerateDataKey`/`DescribeKey`. 관리자(루트)와 사용자(ECS) **분리**.
- **alias** `alias/securevoice-dev-master-key` — 키 ID 대신 사람이 읽는 이름표.

**왜:** 생체정보 자물쇠를 **AWS 공용키가 아니라 우리 전용키**로 가져야 ⓐ 누가 풀 수 있는지(정책) 통제하고 ⓑ 회전·감사·삭제보호 같은 **컴플라이언스 요구**를 만족. lockout은 복구 불가라 옵션A로 **안전하게** 시작.

**어디:** audio/model 버킷 SSE-KMS, ECS api/worker 태스크가 복호화에 사용.

**❓ 드릴 (보지 말고 말로):**
- Q1. AWS가 공짜로 주는 기본 키(aws/s3) 두고 **굳이 CMK를 직접 만든 이유**는?
- Q2. 키 정책 statement 1(루트 `kms:*`)을 **왜 남겨뒀나**? 빼면 더 안전한 거 아닌가? (옵션A vs B)
- Q3. `deletion_window_in_days = 30`이 막아주는 사고 시나리오를 말해보라.
- Q4. statement 2에서 ECS 역할에 `Encrypt`는 안 주고 `Decrypt`·`GenerateDataKey`만 준 건 무슨 의미?

**💡 모범답안:**
- A1. ① **접근통제**: 누가 이 키로 복호화할 수 있는지 **키 정책으로 직접 제한**(기본키는 계정 IAM에 통으로 열림). ② **회전·삭제보호·감사** 같은 보안기능을 우리가 켜고 통제. ③ 생체정보용이라 **전용 키로 격리**(폭발 반경 축소). → 한마디로 "통제권·격리·컴플라이언스".
- A2. 옵션A는 **lockout(키에서 스스로 잠겨 복구 불가) 방지**가 목적. 루트 `kms:*`를 빼고 사용 주체를 전부 열거하다 **하나라도 누락하면 키를 영영 못 쓰게** 됨(AWS 지원도 복구 불가). 운영 중인 키라 **안전 우선**으로 루트를 남김. 더 엄격한 옵션B(루트 제거 + `ViaService=s3` 제한)는 **비운영에서 테스트 후** 2회차에 적용. → "엄격함보다 잠금사고 회피를 우선한 의도적 선택".
- A3. 누군가(실수·악의·랜섬웨어) 키를 **삭제**하면, 그 키로 암호화한 **모든 음성·모델이 영구 복호화 불가**(데이터 전손). 30일 타임록은 그 사이 **알아채고 취소(cancel)** 할 시간을 벌어주는 **마지막 안전망**.
- A4. **암호화는 S3 서비스가 데이터키로 알아서** 하고, ECS는 **읽을 때 복호화(Decrypt)** 와 **새 데이터키 발급(GenerateDataKey)** 만 필요. 딱 필요한 동작만 = **최소권한**. (`kms:*`나 키 삭제권 같은 건 안 줌)

## 카드 4. SSE-KMS 정적 암호화 강제 + S3 Bucket Key

**흐름:** 누가 음성/모델 객체를 S3에 올림 (암호화 옵션 안 줘도) → 버킷의 **기본 암호화 규칙이 자동 발동** → 카드3의 우리 전용 CMK로 **무조건 SSE-KMS 암호화돼 저장** → 디스크에 평문으로 떨어지는 일이 없음. + **Bucket Key**로 KMS 호출은 확 줄임.

**무엇:**
- `aws_s3_bucket_server_side_encryption_configuration` (audio + model 버킷) — 버킷에 **기본 암호화 규칙**을 박음.
- `sse_algorithm = "aws:kms"` — S3 기본키(SSE-S3)가 아니라 **SSE-KMS**(우리가 통제하는 KMS 키로 암호화).
- `kms_master_key_id = aws_kms_key.securevoice_master.arn` — 카드3의 **전용 CMK**를 자물쇠로 지정.
- `bucket_key_enabled = true` — **S3 Bucket Key**. 객체마다 KMS를 부르지 않고 **버킷 단위 데이터키를 캐싱·재사용** → KMS API 호출·비용 대폭 절감 (보안 수준은 동일).

**왜:**
- ① **"강제"가 핵심**: 기본 암호화를 박아두면 클라이언트가 암호화 헤더를 깜빡해도 **자동으로 암호화**됨 → 사람 실수로 평문 저장되는 사고 차단(안전망).
- ② **SSE-S3가 아니라 SSE-KMS인 이유**: 누가 풀 수 있는지를 **키 정책으로 통제**(카드3)하고 **CloudTrail로 복호화 감사**까지 가능. 생체정보라 "AWS가 알아서"보다 우리가 통제하는 키가 필요.
- ③ **Bucket Key 이유**: SSE-KMS는 객체 Put/Get마다 KMS를 호출 → 트래픽 많으면 **KMS 비용·호출량 폭증**. Bucket Key는 KMS 호출을 버킷 레벨로 묶어 **최대 99%까지 절감**.

**어디:** audio(음성 원본) + model(AI 모델) 버킷. RDS는 `aws/rds` 기본키라 이 키의 consumer 아님(카드3 참조).

**용어:** **봉투 암호화(envelope encryption)** — KMS 마스터키로 직접 데이터를 안 풀고, **데이터키(DEK)**를 발급(`GenerateDataKey`)해 그걸로 객체를 암호화. 마스터키는 데이터키만 감싼다(봉투). 카드3에서 ECS에 `GenerateDataKey`를 준 이유와 직결.

**❓ 드릴 (보지 말고 말로):**
- Q1. SSE-S3(기본키)와 SSE-KMS(우리 CMK)의 차이는? 왜 굳이 KMS를 골랐나?
- Q2. "암호화를 강제한다"는 게 정확히 어떻게 작동하나? 클라이언트가 암호화 옵션을 안 주면?
- Q3. `bucket_key_enabled = true`는 무엇을 절감하나? 보안은 약해지지 않나?
- Q4. 카드3(KMS)과 이 카드(SSE-KMS)는 어떻게 이어지나? (봉투 암호화로 설명)

**💡 모범답안:**
- A1. SSE-S3는 **AWS가 키를 통째로 관리**(누가 풀 수 있는지 우리가 통제 불가, 키 정책·감사 없음). SSE-KMS는 **우리 CMK**라 ⓐ 키 정책으로 복호화 주체 제한(ECS 역할만) ⓑ 복호화를 CloudTrail로 감사 ⓒ 회전·삭제보호. 생체정보라 **통제·감사 가능한 KMS**를 택함.
- A2. 버킷에 **기본 암호화 규칙**을 박아두면, 객체 Put 시 암호화 헤더가 없어도 S3가 **그 규칙대로 자동 SSE-KMS 적용**. → 개발자가 깜빡해도 평문 저장 불가능 = **사람 실수에 안 뚫리는 안전망**. (퍼블릭 차단과 같은 "강제 가드레일" 철학)
- A3. **KMS API 호출량과 비용**을 절감(SSE-KMS는 객체마다 KMS 호출 → 트래픽 많으면 비쌈). Bucket Key는 버킷 단위 데이터키를 캐싱·재사용해 호출을 묶음. **데이터는 여전히 같은 CMK로 SSE-KMS 암호화** → 보안 동일, 비용만 down.
- A4. 카드3에서 **CMK(마스터키)** 와 **ECS에 `GenerateDataKey`/`Decrypt`** 를 줬음. 여기서 객체를 저장할 때 S3가 그 CMK로 **데이터키(DEK)를 발급받아**(GenerateDataKey) 객체를 암호화하고, 읽을 때 ECS가 **Decrypt**로 데이터키를 풀어 복호화. = **봉투 암호화**. 카드3은 "자물쇠와 열쇠 권한", 카드4는 "그 자물쇠를 S3에 실제로 채우는 설정".

## 카드 5. OAC (CloudFront만 S3 접근, SigV4)

**흐름:** 사용자가 웹사이트 접속 → CloudFront가 S3(web-static)에서 파일을 가져올 때 **SigV4 서명을 붙여(OAC)** 요청 → S3 버킷 정책이 **"이 특정 CloudFront 배포에서 온 요청만 허용"** → 통과. 반대로 누가 **S3 버킷 URL로 직접** 접근하면 서명이 없어 **거부**.

**무엇:**
- `aws_cloudfront_origin_access_control` (OAC) — CloudFront가 S3로 요청할 때 **항상**(`signing_behavior=always`) **SigV4**(`signing_protocol=sigv4`) 서명을 붙이게 하는 컨트롤러. origin_type=`s3`.
- `data.aws_cloudfront_distribution.cf` — 콘솔로 만든 **실물 CloudFront 배포(ID)** 를 읽어옴(ARN 확보용).
- `aws_s3_bucket_policy.web_static_oac_policy` — web-static 버킷 정책:
  - `Principal = cloudfront.amazonaws.com` (CloudFront 서비스만)
  - `Action = s3:GetObject` (읽기만 — 정적파일은 다운로드만)
  - `Condition: aws:SourceArn = <우리 CloudFront 배포 ARN>` (그 배포 하나만)
- ⚠️ **audio 버킷 OAC 정책은 제거함**(2026-06-23). audio는 SSE-KMS인데 KMS 키정책에 CloudFront 복호화 권한이 없어 CloudFront로 서빙 불가 = 죽은 설정. 음성은 API/프리사인드 URL 경로라 CloudFront 직접 대상도 아님.

**왜:**
- ① **버킷 직접 접근 차단**: S3 URL을 알아내도 CloudFront(+WAF)를 거치지 않으면 못 봄 → **CloudFront가 유일한 정문**. (오리진 우회 차단 — SG의 PrefixList→ALB와 같은 철학)
- ② **퍼블릭 안 열고도 서빙**: 버킷은 퍼블릭 차단(카드1) 유지한 채, "CloudFront만" 정책으로 콕 집어 허용 → **퍼블릭이 아님**(SourceArn 조건). 이중방어.
- ③ OAC는 구식 OAI의 후속으로 **SigV4 + SSE-KMS 지원** 등 최신 표준.

**어디:** web-static(React 정적파일) 버킷. audio는 적용 안 함(위 ⚠️ 사유).

**용어:**
- **OAC(Origin Access Control)** = "CloudFront만 S3 오리진에 접근하게 하는 신분증". 구버전은 OAI.
- **SigV4** = AWS 최신 요청 서명 방식. CloudFront가 "나 진짜 그 배포 맞아"를 서명으로 증명.
- **오리진(Origin)** = CloudFront가 원본을 가져오는 뒷단(여기선 S3).

**❓ 드릴 (보지 말고 말로):**
- Q1. OAC가 정확히 막는 공격/실수는? S3 버킷 URL을 알아낸 사람이 직접 접근하면?
- Q2. 버킷은 퍼블릭 차단(카드1)인데, 어떻게 CloudFront는 읽을 수 있나? 모순 아닌가?
- Q3. audio(음성) 버킷엔 왜 OAC 정책을 **안** 걸었나? (정직 포인트)
- Q4. SG의 "CloudFront PrefixList→ALB만 443"과 이 OAC는 무슨 공통점이 있나?

**💡 모범답안:**
- A1. **S3 직접 접근(오리진 우회)** 을 막음. 버킷 URL을 알아도 SigV4 서명이 없으면 버킷 정책의 `Principal=cloudfront + SourceArn` 조건에 안 맞아 **거부**. → CloudFront(+WAF)를 반드시 거치게 강제.
- A2. 모순 아님. 퍼블릭 차단은 `Principal:*`(누구나) 만 막음. OAC 정책은 **특정 서비스(cloudfront) + 특정 배포 ARN** 조건이라 '퍼블릭'이 아니라 '콕 집은 허용' → 통과. (문지기 정책 + 퍼블릭 차단 안전망 = 카드1 A2와 동일 논리)
- A3. audio는 **SSE-KMS**(우리 CMK)로 암호화되는데 **KMS 키정책에 CloudFront 복호화 권한이 없어** CloudFront가 객체를 못 풂 = 서빙 불가. 게다가 음성(생체정보)은 **API/프리사인드 URL** 로만 주고받아 CloudFront 직접 대상이 아님 → OAC 정책은 **실효 없는 죽은 설정**이라 제거. (web-static은 비암호화 정적파일이라 OAC 정상 동작 → 유지). "동작 안 하는 설정은 남기지 않는다"는 위생.
- A4. 둘 다 **"정문 하나만 두고 옆문(우회)을 막는"** 같은 패턴. SG는 ALB를 CloudFront PrefixList에서 오는 443만 허용(ALB 직접접근 차단), OAC는 S3를 그 CloudFront 배포에서 오는 요청만 허용(버킷 직접접근 차단). → **모든 트래픽을 CloudFront+WAF라는 단일 검문소로 수렴**시키는 설계.

## 카드 6. SG 체이닝 (ECS→RDS 3306 / CloudFront PL→ALB 443)

**흐름:** 트래픽이 단계별로 흐름(CloudFront→ALB→ECS→RDS) → 각 단계의 보안그룹이 **"바로 앞 단계에서 온 것만"** 허용 → 사슬(chain)처럼 연결. IP 주소가 아니라 **앞단의 신분증(SG ID)** 으로 허용.

**무엇:**
- **ECS → RDS (3306):** RDS SG의 인바운드를 `source_security_group_id = ECS SG` 로 지정. → **ECS 태스크에서 온 것만** DB 접근. (CIDR 아님)
- **CloudFront PrefixList → ALB (443):** ALB SG 443 인바운드를 `0.0.0.0/0` 대신 `prefix_list_ids = [com.amazonaws.global.cloudfront.origin-facing]` 로 지정. → **CloudFront 엣지 IP에서 온 것만** ALB 진입.
- **데이터소스 룩업:** 팀이 만든 실물 SG(rds/ecs/alb/vpce)를 **이름으로 검색**해 참조 → 내 레이어는 규칙만 얹음(소유는 타 레이어).

**왜:**
- ① **IP가 아니라 신분(SG)으로 통제**: ECS 태스크가 죽고 새로 떠서 IP가 바뀌어도, **SG 신분증은 그대로**라 규칙 수정 불필요 + 딱 그 그룹만 허용 = 최소권한.
- ② **오리진 우회 차단(ALB)**: `0.0.0.0/0`이면 누구나 ALB 직접 타격 → CloudFront+WAF 우회. PrefixList로 **CloudFront 엣지만** 들이면 정문 일원화(카드5 OAC와 같은 철학).
- ③ **DB 직접 접근 차단(RDS)**: 생체정보가 든 DB는 **앱(ECS)을 거치지 않고는** 어떤 경로로도 직접 못 붙음. 측면이동(lateral movement) 방어.

**어디:** RDS SG(3306), ALB SG(443). 둘 다 data 룩업으로 참조.

**용어:**
- **SG 체이닝** = 한 SG의 규칙에서 **다른 SG를 소스로** 지정(`source_security_group_id`). IP 대신 신분 기반.
- **Managed Prefix List** = AWS가 관리·갱신하는 IP 묶음. CloudFront 엣지 IP는 수시로 바뀌므로 AWS가 유지하는 목록을 그대로 참조(내가 IP 관리 안 해도 됨).

**🔥 실전(정직 포인트 — 드리프트 사고):**
- VPCE SG의 옛 `443 ← 10.0.0.0/22`(VPC 전체) 규칙을 **코드에서 제거**함. 사유: 소유 레이어가 만든 실제 규칙(`443 ← 10.0.1.0/25`, `10.0.0.128/25`)이 이미 있는데 /22는 그걸 다 덮는 **더 넓은 중복** → 유지하면 최소권한을 오히려 약화.
- 또 팀원이 ALB의 443-from-CloudFront 규칙을 콘솔에서 회수한 **드리프트**를 CloudTrail/Athena로 추적·특정 → 코드로 복원. (운영 6장 연계)

**❓ 드릴 (보지 말고 말로):**
- Q1. `source_security_group_id`(SG 체이닝)와 그냥 `cidr_blocks`(IP)로 여는 것의 차이? 왜 SG를 소스로?
- Q2. ALB 443을 `0.0.0.0/0` 대신 CloudFront PrefixList로 묶은 이유? 무슨 우회를 막나?
- Q3. RDS는 왜 ECS SG에서만 3306을 허용하나? 막는 사고 시나리오는?
- Q4. VPCE의 `/22` 규칙은 왜 코드에서 **지웠나**? (최소권한/소유권 관점)

**💡 모범답안:**
- A1. IP(CIDR)는 인스턴스가 재기동되면 **바뀌고**, 대역으로 열면 그 안의 다른 것까지 포함됨. **SG 체이닝은 "그 그룹 소속이면 IP 무관하게 허용"** → ⓐ IP 변동에 안 깨지고 ⓑ 딱 그 그룹만 허용해 **가장 타이트**. 클라우드(동적 IP) 환경의 정석.
- A2. ALB가 `0.0.0.0/0`이면 누구나 ALB로 **직접** 들어와 CloudFront와 **WAF를 우회**(프로젝트 핵심 통제 무력화). PrefixList는 **CloudFront 엣지 IP만** 허용 → 모든 외부 트래픽이 CloudFront+WAF를 반드시 거치게 강제. (OAC와 똑같이 "정문 하나")
- A3. RDS는 **ECS(앱)에서 온 것만** 3306 허용 → 베스천·다른 서브넷·인터넷 등 **어디서도 DB 직접 접속 불가**. 막는 사고: 공격자가 네트워크 어딘가에 발을 들여도 **DB로의 측면이동 차단**, 생체정보가 든 DB 직접 탈취 방지.
- A4. /22(VPC 전체)는 소유 레이어가 이미 박아둔 **실제 서브넷 `/25` 2개를 모두 덮는 더 넓은 중복** 규칙. 유지하면 **최소권한을 약화**(넓게 여는 셈). + 그 SG의 **소유는 타 레이어**라 인입 통제를 `/25`에 일임하고 내 레이어는 손대지 않는 게 맞음(변경창구 일원화). → "넓은 중복은 지우고, 소유 레이어에 맡긴다."

## 카드 7. 워커 Zero-Inbound 격리

**흐름:** AI 워커는 누가 "처리해줘"라고 **연결(push)** 하지 않음 → 워커가 스스로 **SQS 큐에서 일감을 꺼내옴(pull, 아웃바운드)** → 결과를 S3에 올림 → **외부에서 워커로 들어올 일이 전혀 없음** → 인바운드 규칙 0개로 격리.

**무엇:**
- `aws_security_group.worker_runtime_isolation` — 워커 전용 SG **신규 생성**.
- **`ingress` 블록을 아예 안 씀** → 인바운드 전면 차단(인터넷·ALB·다른 SG 등 **그 무엇도** 워커 포트로 못 들어옴, 프로토콜 레벨 드롭).
- **`egress`만 개방** — `protocol="-1"`(전체), `0.0.0.0/0` → SQS 폴링 + S3 업로드 + ECR 이미지 다운로드용 (NAT/VPCE 경유).

**왜:**
- ① **비동기 워커는 인바운드가 필요 없다**: 일을 **받는(push)** 게 아니라 큐에서 **가져오는(pull)** 구조라, 외부 진입점 자체가 불필요 → 열면 그게 곧 공격 표면.
- ② **공격 표면 0**: 들어올 문이 없으면 포트스캔·취약점 익스플로잇·무차별 접속 시도가 **네트워크 레벨에서 원천 차단**. 가장 강력한 격리.
- ③ 생체정보(음성)를 실제로 처리하는 워커라 **가장 민감** → 가장 강하게 격리.

**어디:** 비동기 AI 워커 태스크 전용 SG. (api 태스크는 ALB 뒤라 인바운드 필요 → 별개)

**용어:** **Zero-Inbound** = 인바운드 규칙이 0개. SG는 **기본 deny**라 규칙을 안 쓰면 전부 막힘(아웃바운드만 따로 허용).

**🔥 정직 포인트(개선 여지):**
- 인바운드는 완벽히 0인데, **아웃바운드(egress)는 `0.0.0.0/0` + 전체 프로토콜로 넓다.** SQS/S3/ECR 통신 편의를 위해 열어둔 것.
- 더 엄격히 하려면: **VPC 엔드포인트(S3/SQS/ECR) 경유로 좁히고** egress 목적지를 그 엔드포인트/PrefixList로 한정 가능. (데이터 유출 통로 축소) → 발표 시 "인바운드는 제로, 아웃바운드는 추후 VPCE로 조이는 게 정석"으로 솔직하게.

**❓ 드릴 (보지 말고 말로):**
- Q1. 인바운드 규칙을 **아예 안 쓴** 게 어떻게 보안이 되나? 그럼 워커는 일을 어떻게 받나?
- Q2. ALB 뒤 api 태스크는 인바운드가 필요한데, 워커는 왜 0이어도 되나? (push vs pull)
- Q3. Zero-Inbound가 막는 공격을 구체적으로?
- Q4. (정직) egress가 `0.0.0.0/0`·전체 프로토콜로 넓은데 괜찮나? 어떻게 개선하나?

**💡 모범답안:**
- A1. SG는 **기본 deny**라 ingress 규칙을 안 쓰면 **모든 인바운드가 막힘**. 워커는 외부 연결을 받을 필요가 없고, **SQS 큐에서 일감을 스스로 꺼내(아웃바운드 pull)** 처리 → 들어오는 문이 없어도 정상 동작.
- A2. api는 사용자 요청을 **받아야**(push) 해서 ALB→인바운드가 필수. 워커는 큐를 **폴링해 가져오는(pull)** 구조라 누가 연결해 줄 필요가 없음 → **인바운드 0이 가능**. (구조가 격리를 허용)
- A3. 들어올 문이 없으니 **포트 스캔·서비스 취약점 익스플로잇·무차별 접속**이 **네트워크 레벨에서 원천 드롭**. 워커가 직접 노출되는 경로 자체를 제거 = 공격 표면 최소화.
- A4. 현재는 SQS/S3/ECR 통신을 위해 넓게 열어둠(편의). 개선: **VPC 엔드포인트(S3 Gateway/SQS/ECR Interface)로 트래픽을 사설 경로화**하고 egress 목적지를 그 엔드포인트로 **한정** → 인터넷으로의 데이터 유출 통로를 좁힘. "인바운드 제로는 끝냈고, 아웃바운드 최소화는 2차 과제"로 솔직하게.

## 카드 8. IAM 하드닝 (ListBucket 버킷 한정 + 무수정 attach)

**흐름:** ECS api/worker 태스크가 S3 버킷을 조회(List)해야 함 → 권한을 줄 때 **모든 버킷(`*`)이 아니라 audio·model 두 버킷만** 콕 집은 정책을 만듦 → 팀이 만든 역할을 **수정하지 않고** 내 레이어에서 **attach**.

**무엇:**
- `aws_iam_policy.ecs_s3_list_hardening` — `s3:ListBucket` 을 `Resource = [audio.arn, model.arn]` **두 버킷으로만** 한정(`*` 아님).
- `data.aws_iam_role` (api/worker) — 팀(20-runtime)이 만든 실물 역할을 **이름으로 룩업**.
- `aws_iam_role_policy_attachment` ×2 — 그 역할에 **정책만 추가 결합**. 팀 코드는 한 줄도 안 건드림.

**왜:**
- ① **최소권한(Least Privilege)**: 꼭 필요한 버킷(음성·모델)에만 List 허용. `Resource="*"` 였다면 **계정의 모든 버킷 목록**을 볼 수 있어 정보 노출·권한 남용 위험.
- ② **레이어 분리/소유권 존중**: 팀 역할을 직접 수정하면 충돌·드리프트 위험 → **attach만** 하면 내 보안정책을 얹으면서 팀 코드와 안 부딪힘.
- ③ **403 오탐 방지(실용)**: 버킷 존재 조회가 막혀 나던 403을 List 권한으로 해소 — 권한은 주되 **딱 그 버킷만**.

**어디:** api-task-role, worker-task-role (둘 다 audio/model List).

**용어:**
- **최소권한** = 일을 하는 데 **딱 필요한 만큼만** 권한 부여.
- **ListBucket vs GetObject** = ListBucket은 **버킷 레벨**(목록 보기, Resource=버킷 ARN), GetObject는 **객체 레벨**(파일 읽기, Resource=버킷 ARN`/*`). 여기선 목록 조회라 ListBucket.
- **Attach** = 기존 역할에 정책을 **갖다 붙이기**(역할 정의 자체는 안 바꿈).

**❓ 드릴 (보지 말고 말로):**
- Q1. ListBucket을 `Resource="*"` 대신 audio/model 두 버킷으로 **한정**한 게 왜 중요한가?
- Q2. 팀이 만든 역할을 **직접 수정 안 하고** 정책 attach로 얹은 이유는?
- Q3. ListBucket(버킷 레벨)과 GetObject(객체 레벨)는 뭐가 다른가? 여기선 왜 ListBucket?
- Q4. 최소권한을 한 문장으로? 와일드카드(`*`)가 왜 위험한가?

**💡 모범답안:**
- A1. `*`면 **계정의 모든 버킷 이름·목록**을 볼 수 있어 정보 노출 + 만약 역할이 탈취되면 피해 반경이 전 버킷으로 확대. 두 버킷으로 한정하면 **딱 필요한 곳만** + **폭발 반경 축소**. (최소권한)
- A2. 팀 역할 정의를 직접 고치면 ⓐ 팀 코드와 **충돌/드리프트**, ⓑ 소유권 경계 침범. **attach는 정책만 추가 결합**이라 팀 코드를 안 건드리고 내 보안 통제를 얹을 수 있음 → 레이어 분리·변경창구 일원화 유지.
- A3. ListBucket은 **버킷 안 목록 조회**(Resource=버킷 ARN), GetObject는 **개별 파일 다운로드**(Resource=버킷 ARN+`/*`). 여기선 "버킷 존재/목록 확인"이 목적이라 ListBucket만 부여(파일 읽기 권한은 별도, 필요 최소만).
- A4. "각 주체에게 **일에 꼭 필요한 권한만, 필요한 자원에만** 준다." `*`는 **현재·미래의 모든 자원**까지 포함돼 의도치 않은 광범위 접근을 열고, 탈취 시 피해가 통제 불가로 커지므로 위험.

## ✅ 예방(Prevention) 카드 1~8 완료 — 한 줄씩 복습

1. **S3 퍼블릭 차단** — ACL 2 + 정책 2로 모든 퍼블릭 경로 봉쇄(안전망).

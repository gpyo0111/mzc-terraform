# 🛠️ 05. 대응 (Response) — 공부 카드 (방식②)

> 사용법: 카드 읽기 → ❓드릴 질문에 **말로 답** → **모범답안**과 대조 → 보강.
>
> 큰 그림: 탐지(03)·알림(04)이 "보고 알린다"면, 대응(05)은 **"사람 없이 자동으로 되돌린다"(self-healing)**.
> `사건 → EventBridge(04와 동일 규칙 재사용) → Lambda → 자동 회수/복구 + SNS 보고`.
> 이게 **필살기**: 위협을 탐지·알림에서 멈추지 않고 **자동 원상복구**까지.

## 카드 1. SG 자동대응 Lambda (0.0.0.0/0 위험 개방 자동 회수)

**흐름:** 누가 보안그룹에 위험 포트(22/3306 등)를 `0.0.0.0/0`으로 개방 → EventBridge(SG 변경 규칙)가 Lambda 호출 → Lambda가 **해당 SG를 재조회**해 실제 열린 위험 규칙만 추려 → (드라이런이면 알림만 / 회수ON이면 그 규칙만 revoke) → SNS 보고.

**무엇:**
- `aws_lambda_function.sg_auto_remediate` (python3.12) + 실행 IAM 역할 + 전용 로그그룹(30일).
- **트리거 재사용**: 새 규칙 안 만들고 기존 `sg_rule_changes`(04 카드3) 규칙에 **Lambda 타깃만 추가** → 알림(SNS)과 자동대응(Lambda)이 **같은 트리거 공유**(룰/요금 중복 없음).
- `aws_lambda_permission` — EventBridge가 이 Lambda 호출하도록 허용.
- **토글** `var.sg_auto_revoke_enabled` (기본 false=드라이런) → env `AUTO_REVOKE`.

**파이썬 로직(핵심):**
- 처리 이벤트: `AuthorizeSecurityGroupIngress`(규칙 추가) + `ModifySecurityGroupRules`(기존 규칙 편집). egress·기타는 skip.
- **이벤트를 직접 파싱하지 않고 groupId로 SG 현재 상태를 재조회** → "지금 실제로 열린" 규칙만 처리(이벤트 형식 의존·오작동 최소화).
- 대상 = **위험 포트(RISKY_PORTS: 22/23/21/3389/3306/5432/1433/6379/11211/27017/9200) 또는 전체포트(-1)** 에 `0.0.0.0/0`·`::/0` 인 인바운드.
- **예외 태그**: SG에 `AutoRemediate=false` 면 건드리지 않음(의도적 개방 허용).
- 회수 시 **문제 CIDR만 골라 그 규칙만 revoke**(SG·다른 규칙 보존).

**왜:**
- ① **대응의 자동화**: 위험 개방은 **분초를 다툼**(노출되는 순간 스캔당함) → 사람이 메일 보고 손쓰기 전에 Lambda가 즉시 회수.
- ② **안전 설계 3중**: ⓐ 위험 포트+전체개방만 좁혀 정상 변경 오회수 방지, ⓑ 드라이런 기본값으로 오탐 관찰 후 회수 활성화, ⓒ 예외 태그로 의도적 개방 허용.
- ③ **재조회 방식**: 이벤트 JSON을 신뢰하지 않고 SG 실제 상태를 다시 봐서 **"진짜 지금 열려있는 것만"** 처리 → 오작동·과회수 방지.

**🔥 정직 포인트:**
- 현재 **드라이런(알림만)** 상태로 배포됨 → 데모/발표 때 `sg_auto_revoke_enabled=true`로 켜서 실제 자동회수 시연 예정.
- `ec2:DescribeSecurityGroups`는 **리소스 수준 권한 미지원(AWS 제약)** 이라 `Resource="*"` 불가피. 회수(Revoke)는 이 계정/리전 SG로 한정.

**어디:** 계정 내 보안그룹(서울). 트리거 = SG 변경 EventBridge 규칙. 보고 = 서울 SNS.

**용어:**
- **self-healing(자가복구)** = 사람 개입 없이 시스템이 위반을 스스로 원상복구.
- **드라이런(dry-run)** = 실제 조치(회수)는 안 하고 "했을 것"만 알림 → 오탐 관찰용.
- **revoke** = 보안그룹 규칙 회수(삭제).

**❓ 드릴 (보지 말고 말로):**
- Q1. 이 Lambda가 막는 사고와, "알림만"(04)이 아니라 "자동회수"까지 한 이유는?
- Q2. 이벤트 JSON을 그대로 안 쓰고 **SG를 재조회**하는 이유는?
- Q3. 오회수(정상 변경을 잘못 막음)를 방지하는 안전장치 3가지는?
- Q4. 새 EventBridge 규칙을 안 만들고 기존 규칙을 재사용한 이유는?

**💡 모범답안:**
- A1. 보안그룹에 **위험 포트가 인터넷 전체(0.0.0.0/0)로 열리는 사고**(WAF·SG 우회, 즉시 포트스캔 표적). 위험 개방은 **노출되는 순간부터 분초 단위로 스캔·공격**당하므로, 사람이 메일 보고 손쓰기 전에 **Lambda가 자동 회수**해 노출 창을 최소화 → 알림(04)을 넘어 대응(05)으로 승격.
- A2. CloudTrail/EventBridge 이벤트 형식은 케이스마다 다르고(키 대소문자 등), 이벤트 시점과 현재 상태가 다를 수 있음. **groupId로 SG 현재 상태를 재조회**하면 "지금 실제로 열려 있는 규칙만" 정확히 처리 → **이벤트 파싱 의존·오작동을 최소화**.
- A3. ⓐ **대상 한정**: 위험 포트(또는 전체포트)에 0.0.0.0/0·::/0 인 것만 → 정상 변경은 안 건드림. ⓑ **드라이런 기본값**: 처음엔 회수 없이 알림만 → 오탐 0 확인 후 켬. ⓒ **예외 태그**(`AutoRemediate=false`): 의도적으로 열어둔 SG는 건너뜀.
- A4. 같은 사건(SG 변경)에 **알림과 자동대응이 둘 다 필요**한데, 규칙을 새로 만들면 **룰 중복·요금 중복**. 기존 `sg_rule_changes` 규칙에 **타깃만 추가**하면 한 트리거로 SNS(알림)+Lambda(대응)를 동시에 → 깔끔하고 중복 없음.

## 카드 2. CloudTrail 자동복구 Lambda (StopLogging/DeleteTrail 원복)

**흐름:** 누가 CloudTrail을 끄거나(StopLogging) 지움(DeleteTrail) → EventBridge(CloudTrail 변조 규칙)가 Lambda 호출 → (드라이런이면 알림만 / 복구ON이면) **로깅 재가동 또는 트레일을 원래 설정대로 재생성** → SNS 보고.

**무엇:**
- `aws_lambda_function.cloudtrail_auto_recover` (python3.12) + IAM 역할 + 로그그룹(30일).
- **트리거 재사용**: 기존 `cloudtrail_tampering`(04 카드3) 규칙에 Lambda 타깃만 추가.
- **토글** `var.cloudtrail_auto_recover_enabled` (기본 false=드라이런) → env `AUTO_RECOVER`.
- **env로 원래 설정 주입**: `TRAIL_NAME`/`S3_BUCKET`/`IS_MULTI_REGION`/`INCLUDE_GLOBAL`/`ENABLE_VALIDATION`/`DATA_RESOURCE_ARN`을 **실제 트레일 속성에서** 주입 → 코드/실물 항상 일치.

**파이썬 로직(핵심):**
- 처리 이벤트: **StopLogging**(→ `start_logging` 재가동) + **DeleteTrail**(→ `create_trail` 원설정대로 재생성 + 데이터이벤트(uploads/) 재적용 + `start_logging`).
- **우리 트레일만**(`_is_our_trail`): name이 우리 트레일명/ARN과 일치할 때만 동작(타 트레일 오작동 방지).
- **UpdateTrail/PutEventSelectors는 자동복구 안 함** → 정상 Terraform 변경과 충돌 방지(알림만 유지).

**왜:**
- ① **로그는 항상 켜져 있어야 함**: CloudTrail은 모든 탐지·알림·조사·생체정보 감사의 **토대**(03 카드1). 끄면 그 직후 공격이 **로그 공백** 속에 진행 → 소급 복구 불가.
- ② **공격자의 first move**: 로그 끄기(T1562)는 침해 후 **흔적 지우기 첫 수순** → 자동 재가동으로 **공백을 최소화**.
- ③ **재생성 설정 일치**: 삭제 후 재생성 시 원래 속성(멀티리전·무결성검증·데이터이벤트)을 그대로 복원해야 의미 → env 주입으로 코드/실물 동기화.

**🔥 정직 포인트:**
- 현재 **드라이런** 배포 → 발표 때 `cloudtrail_auto_recover_enabled=true`로 켜서 시연 예정.
- `create_trail`은 **정지 상태**로 만들어져 `start_logging`을 따로 호출해야 함(코드에 반영).
- UpdateTrail/PutEventSelectors를 자동복구 대상에서 뺀 건 **정상 Terraform 변경(apply)** 까지 되돌려버리면 운영이 망가지기 때문 → 끄기/삭제만 자동복구.

**어디:** 우리 트레일(securevoice-dev-trail). 트리거 = CloudTrail 변조 규칙. 보고 = 서울 SNS.

**용어:**
- **StopLogging** = 트레일은 두고 로깅만 중단. **DeleteTrail** = 트레일 자체 삭제.
- **T1562 (Impair Defenses)** = 방어/로깅 무력화(MITRE ATT&CK).

**❓ 드릴 (보지 말고 말로):**
- Q1. CloudTrail이 꺼지면 왜 치명적인가? 왜 "자동복구"까지 필요한가?
- Q2. StopLogging과 DeleteTrail 복구 방식이 어떻게 다른가?
- Q3. UpdateTrail/PutEventSelectors는 왜 자동복구 대상에서 뺐나?
- Q4. 재생성에 필요한 설정값을 코드에 박지 않고 env로 주입한 이유는?

**💡 모범답안:**
- A1. CloudTrail은 모든 탐지·알림·조사·생체정보 감사의 **데이터 토대**라, 꺼진 동안의 활동은 **기록이 안 남아 소급 복구 불가**(로그 공백). 게다가 로그 끄기는 공격자의 **흔적 지우기 첫 수순(T1562)** → 그 직후 본 공격이 진행될 가능성이 높음 → 사람이 손쓰기 전 **자동 재가동**으로 공백을 최소화해야 함.
- A2. **StopLogging**은 트레일은 살아있고 로깅만 멈춘 것 → `start_logging`으로 다시 켜면 끝. **DeleteTrail**은 트레일 자체가 사라진 것 → `create_trail`로 **원래 설정대로 재생성**하고, 데이터이벤트(uploads/)를 다시 적용한 뒤 로깅을 시작해야 함(생성 직후엔 정지 상태라).
- A3. UpdateTrail·PutEventSelectors는 **정상적인 Terraform 변경(apply)** 으로도 발생함. 이걸 자동으로 되돌리면 **운영상 정당한 변경까지 파괴** → 끄기/삭제(명백한 변조)만 자동복구하고, 이 둘은 **알림만** 유지(사람 판단).
- A4. 코드에 설정값을 하드코딩하면 **실제 트레일 설정이 바뀔 때 어긋남(드리프트)**. 실제 트레일 속성(`aws_cloudtrail.main.*`)에서 env로 주입하면 **재생성 설정이 항상 실물과 일치** → 복구해도 원래 모습 그대로.

## 카드 3. 자동대응 공통 설계 철학 (두 Lambda 관통)

**흐름:** 두 self-healing Lambda(SG·CloudTrail)는 **같은 설계 원칙**을 공유 → 안전하게 "자동화"를 도입.

**무엇 (공통 5원칙):**
1. **기존 EventBridge 규칙 재사용** — 새 룰 안 만들고 04의 알림 규칙에 Lambda 타깃만 추가 → 알림+대응이 한 트리거. 룰/요금 중복 없음.
2. **드라이런 기본값** — 토글(`*_enabled`) 기본 false → 처음엔 알림만, 오탐/오작동 0 확인 후 켬.
3. **최소권한 IAM** — 회수/복구 액션을 **이 계정·리전·우리 리소스**로만 한정. SNS는 서울 토픽 1개만. (Describe만 `*` — AWS 제약)
4. **env 주입 / 재조회** — 실물에서 설정·상태를 읽어 **코드/실물 일치**, 이벤트 파싱 의존 최소화.
5. **대응 적정선** — "되돌리는 게 거의 항상 정답"인 것(위험 개방 회수·로그 재가동)만 자동화. 정상일 수 있는 것(루트·IAM·UpdateTrail)은 **알림만**.

**왜:**
- ① **자동화의 핵심 위험 = 오작동으로 정상 파괴** → 드라이런·대상한정·예외태그·적정선으로 그 위험을 통제.
- ② **느슨한 결합·중복 제거**: 트리거 재사용으로 알림과 대응을 깔끔히 한 줄기로.
- ③ **최소권한**: 자동대응 역할이 탈취돼도 피해 반경을 우리 리소스로 한정.

**🔥 정직 포인트 (발표 차별화):**
- 이게 프로젝트의 **필살기**: 대부분 "탐지·알림"에서 멈추는데, 여기선 **탐지→알림→자동복구**까지 닫음(closed loop).
- 단, **신중하게**: 드라이런으로 시작 + 자동화 범위를 "안전한 것"에만 한정 = **"자동화를 했다"가 아니라 "안전하게 자동화하는 법을 안다"** 가 어필 포인트.

**❓ 드릴 (보지 말고 말로):**
- Q1. 자동대응(self-healing)의 가장 큰 위험은? 그걸 어떻게 통제했나?
- Q2. 왜 모든 위협을 자동대응하지 않고 일부는 "알림만" 두나? (대응 적정선)
- Q3. "탐지·알림에서 멈추지 않고 자동복구까지"가 왜 차별화 포인트인가?

**💡 모범답안:**
- A1. 가장 큰 위험은 **오작동으로 정상 작업을 자동 파괴**(정상 SG 변경 회수, 정상 트레일 변경 되돌림). 통제: ⓐ **드라이런 기본값**(알림만으로 오탐 관찰), ⓑ **대상 한정**(위험포트+전체개방, 우리 트레일만), ⓒ **예외 태그**, ⓓ **재조회/최소권한**, ⓔ **자동화 범위를 안전한 행위에만** 한정.
- A2. **루트 사용·IAM 변경·UpdateTrail** 같은 건 정상 운영일 수도 있어, 자동으로 되돌리면 정당한 작업을 파괴할 위험이 큼 → **사람 판단(알림)** 에 맡김. 자동화는 **"되돌리는 게 거의 항상 정답"** 인 명백한 위반(위험 개방·로그 끄기)에만 적용 = 대응 적정선.
- A3. 대부분의 보안 구성은 **탐지·알림에서 멈춤**(사람이 와서 손써야 함) → 사람이 자는 새벽·휴일엔 노출 창이 길어짐. 자동복구는 **사람 개입 없이 노출 창을 분초로** 줄여 **closed loop(탐지→대응)** 를 완성. 게다가 "드라이런으로 신중히, 안전한 범위만"이라 **운영 감각**까지 보여줌.

## ✅ 대응(Response) 카드 1~3 — 한 줄씩 복습

1. **SG 자동대응** — 위험포트 0.0.0.0/0 개방 시 재조회 후 그 규칙만 자동 회수(드라이런 기본·예외태그·대상한정).
2. **CloudTrail 자동복구** — StopLogging→재가동 / DeleteTrail→원설정 재생성+로깅시작(우리 트레일만·env 주입).
3. **공통 철학** — 기존 규칙 재사용 + 드라이런 + 최소권한 + 코드/실물 일치 + 대응 적정선(안전한 것만 자동화).

> 관통하는 한 문장: **"탐지·알림에서 멈추지 않고, '되돌리는 게 정답'인 위반(위험 개방·로그 끄기)만 골라 사람 없이 자동 원상복구(self-healing)한다 — 단 드라이런·대상한정·최소권한으로 '안전하게' 자동화한다."**
> 🏁 예방→경계→탐지→알림→대응 5단계 카드 완성. 다음: 캡쳐(`docs/CAPTURE_CHECKLIST.md`).
